## 🎯 总体结论（置信度：高）

**两份文档作为"方案 + 落地计划"的组合是工程化合格的。**

- PROPOSAL 把"为什么做 / 做什么 / 不做什么 / 决策记录"四件套写齐了
- PLAN 用 7 步 + 3 个里程碑把 PROPOSAL 拆成可执行单元
- 范围控制（"先头部队"、"防止范围蔓延"）和 dogfood 机制（每步都 ingest 进 GBrain）是亮点

### 核心优点

1. **"信息层先行，框架层后置"原则与 PLAN 节奏自洽** —— 不在前期硬造打分卡，从板块环境分析这个最直接需求切入
2. **GBrain 作为唯一记忆层**的决策非常果断，避免自建持久化的陷阱
3. **AI 输出"四件套"模板**（结论 + 指标 + 推理链 + 反向信号）与用户偏好高度对齐
4. **PLAN §6 给出 10 分钟可执行的最小动作**，让方案能立刻从"讨论"进入"动手"

## ⚠️ 问题清单（按严重度）

### 🔥 P0-1 — 数据源策略前后不自洽

**现状**：

- PROPOSAL §1.3 设计原则 #3 写："**个人使用，非商业化** —— 数据获取通过用户提供的 cookie 抓取，仅本地存储"
- PROPOSAL §2 范围又写："数据：通过用户 cookie 从主流财经平台抓取"
- PROPOSAL §3.6 进一步规定 cookie 文件位置
- PLAN §5 却明确："Cookie 抓取流程 → 第一阶段只用 akshare / efinance，cookie 化在第二阶段"

**问题**：PROPOSAL 把 cookie 当成"原则级"必选项，PLAN 却推迟到第二阶段。读 PROPOSAL 的人会以为 MVP 就要 cookie，开干时才发现不需要。

**建议修订**：

- 改 PROPOSAL §1.3 设计原则 #3 为：
  > "**数据来源分级**：第一阶段以无 cookie 公开数据源（akshare/efinance）为主；第二阶段引入 cookie 抓取以补全消息面 / 财务深度数据。"
- 在 PROPOSAL §3.6 顶部加一句："仅第二阶段起需要"

---

### 🔥 P0-2 — "MVP" 与 "M3" 含义错位

**现状**：

- PROPOSAL §6 第一阶段（MVP）包含：板块 1 + 板块 2 + 板块 3 + 一句话摘要（**4 项**）
- PLAN §0 总览把 M3 描述为 "**MVP 第一个 Skill 在 Hermes 中可用**" —— 但 M3 实际只覆盖板块 1，离 PROPOSAL 定义的 MVP 还差 3 项
- PLAN §第 7 步自己注释为"MVP 第一刀"，但 §0 总览图和里程碑标签没改口

**问题**：读者会在 M3 完成时误以为 MVP 已交付。

**建议修订**：在 PLAN §0 把 M3 描述明确改为 "**MVP 先头部队（板块 1）跑通**"，并在 §0 末尾追加：

```
M4-M6（本 PLAN 之外） = 板块 2、板块 3、一句话摘要 → 才算完成 PROPOSAL §6 的 MVP
```

### ⚠️ P1-1 — GBrain 不可用时的降级路径缺失

**现状**：

- PROPOSAL §3.3 把 GBrain 定位为"唯一记忆/检索层"
- PROPOSAL §3.2 关键设计是"**Markdown Page 是唯一结构化输出，HTML 由 markdown 派生**"

**问题**：通篇没回答两个问题：

1. GBrain MCP 服务挂了，分析流程是阻塞、报错，还是降级 stateless 继续？
2. ingest 失败时，Markdown Page 是只落盘不入脑，还是回滚整个分析？

个人工具不严格要求高可用，但这关系到"用户在没网或 GBrain 异常时还能不能用"。

**建议修订**：在 PROPOSAL §3.3 末尾加一段"降级策略"：

```
GBrain 仅承担记忆增强，不阻塞主流程：
- ingest 失败 → 仅落盘 Markdown + HTML，记录到本地待重试队列
- query 失败 → 跨次对比降级为"无历史 context"，分析继续
- 用户可通过手动 `gbrain ingest <path>` 后补
```

### ⚠️ P1-2 — "AI 输出四件套"缺少结构化字段映射

**现状**：

- PROPOSAL §5 给出了文本格式（emoji + 中文段落）
- PLAN §第 3 步设计 Schema 时只列了 frontmatter 必含字段（id/type/code/...），**没要求把"四件套"映射到结构化字段**

**反向信号**：未来想做"我上周对宁德的 confidence 是中、这周变成低，触发了什么变化？"这种跨次比对 —— 如果四件套是非结构化文本块，GBrain 只能向量召回相似文本，做不了字段级对比。

**建议修订**：把 PLAN §第 3 步的"必含字段"扩成两层：

- **元数据层**：id / type / code / name / sector / industry / created_at / strategy_refs ...
- **判断层（每个分析模块一个 entry）**：`verdict / confidence / indicators[] / reasoning_chain[] / counter_signals[]`

并把"四件套字段在 Schema 中可被独立查询"作为第 3 步的**显式验证标准**之一。

### ⚠️ P2-1 — "10 秒内拿到简报" SLA 与多模块串行的矛盾

**现状**：PROPOSAL §6 第一阶段承诺："用户输入股票代码，**10 秒内**拿到一份能判断'要不要进一步深看'的简报"

**问题**：MVP 包含板块 1 + 2 + 3 + 一句话摘要，每个板块至少有一次数据拉取 + 一次 LLM 调用：

- 数据抓取（akshare/efinance 网络调用，单次 1-3 秒）
- LLM 推理（带"四件套"prompt 通常 3-8 秒）
- 一句话摘要还要在 3 个模块输出之后做 final 合成

3 个板块即使并行抓数据，**LLM 串行调用就远超 10 秒**。

**建议修订**（三选一）：

1. 改 SLA 到"**30-60 秒**"，与真实工程能力对齐
2. 改成两档承诺："**首屏（板块 1）≤ 15 秒，全 MVP ≤ 60 秒**"
3. 明确说"**10 秒只针对缓存命中场景**"

不改的风险：自己的预期被误导，第二阶段一开始就背 SLA 债。

---

### ⚠️ P2-2 — 回归用例覆盖度不足

**现状**：PLAN §4 选 300750（宁德时代）+ 600519（茅台）作为标准用例。

**反向信号**：两只都是大市值、低换手、低波动的白马，对方案重点要解决的几类场景**几乎无法测试**：

- 板块 1.1 "轮动加速期识别" —— 白马股很少在加速期
- 板块 1.3 "矛盾信号识别"（板块退潮但本股逆势） —— 需要中小盘活跃股
- 数据缺失边界（停牌 / ST / 新股）

**建议修订**：把回归用例扩为 4 只 + 1 类边界：

- 大盘价值（600519 茅台）
- 大盘成长（300750 宁德）
- **新增**：中盘活跃概念股（按当期热门轮动选 1 只）
- **新增**：周期股（如有色 / 化工龙头，验证板块景气度逻辑）
- **新增**：1 个边界 case（停牌或 ST 股，验证错误降级路径）

## 🧠 反向信号（让你保持怀疑）

### RS-1 — 板块 1.2 行业景气度的数据源在 PLAN 中是"黑洞"

PROPOSAL §4 列出 PMI / 一致预期 / 政策导向 / 上下游传导 等指标，但这些 **akshare/efinance 几乎都不提供**。PLAN §5 把 cookie 推到第二阶段，这意味着第 7 步如果坚持做"完整板块 1"就会卡在 1.2。

**建议**：要么把 1.2 推到第二阶段，要么 1.2 在 MVP 阶段降级为"通用版指标"（仅 ROE / 毛利率中位数），不做行业定制模板。

### RS-2 — "用户沉淀自己策略" vs "ingest ZhuLinsen 11 套策略"的隐性张力

已经把 baseline strategies 作为 GBrain 的 `Strategy` 实体提前 ingest，AI 在做判断时大概率会被这些 baseline 框架"拐走"，反而抑制用户自己的判断框架生长。

**建议**：在 PROPOSAL §3.4 的 `Strategy` 实体上加一个 `source: baseline | user_custom` 字段，并在 LLM prompt 里明确"baseline 仅作参考、用户策略优先"。

### RS-3 — PROPOSAL §3.4 决策记录有个表述瑕疵

末尾写"预设 6 个 **Stock 实体类型** + 6 种 typed link"，但实际是"6 种**实体类型**（Stock/Sector/Industry/Strategy/Report/News）+ 6 种 typed link"。Stock 是其中一种，不是分类层级。

**建议**：改成"预设 **6 种实体类型 + 6 种 typed link**"。

### RS-4 — PLAN §第 7 步流程缺了"分析前先 query 历史"

PROPOSAL §3.3 用法分工里明确写了"由 analyze Skill 在分析前调用 query 拿历史摘要"，但 PLAN §第 7 步流程的 6 个步骤里没有这一步（只有最后 ingest 入脑）。

**风险**：第一次跑没问题，但第二次跑相同股票时 AI 不知道历史结论，跨次对比的能力就没了。

**建议**：在 PLAN §第 7 步流程 ① 之后插入新步骤"② 调 GBrain query 拉历史分析摘要（若有）"，原 ②-⑥ 顺延。

### RS-5 — "输入股票代码或名称"的输入解析没明确归属

PROPOSAL §2 明确允许代码或名称作为输入，PLAN §第 7 步流程 ① 写了"resolve 股票代码"，但 PLAN §第 4 步抽 utils 时只标了 `name_to_code_resolver.py` 是"候选"。

**风险**：如果第 7 步真的允许名称输入，第 4 步必须把 resolver 列为**必抽**而非候选。

**建议**：把 PLAN §第 4 步抽取清单中的 `name_to_code_resolver.py` 从"候选"提升为"必抽"。
